===================================================================== 1.
ZWECK
=====================================================================

Diese Quelle definiert den verbindlichen FDShop-Standard für sämtliche
Administrationslisten.

Sie beschreibt: • Listenarchitektur • native
Joomla-6.1-Listenmechanismen • SearchTools • Filter • Statusfilter •
Sortierung • Pagination • Listen-Formulare • ListModel-Regeln •
Filterzustände • technische Listenaktionen • Mehrlisten-Ansichten

Nicht Bestandteil sind Edit-Formulare, Businesslogik, fachliche
Löschentscheidungen, Datenmodell, SQL-Struktur oder Architektur
außerhalb von Administrationslisten.

Gesamtarchitektur -> FDShop_Architektur_Struktur_Installation Fachliche
Status-/Löschregeln -> FDShop_Fachregeln_Daten_und_Formulare

===================================================================== 2.
GELTUNGSBEREICH
=====================================================================

Verbindlich für sämtliche FDShop-Administrationslisten und alle Rollen,
die diese entwickeln, prüfen oder dokumentieren.

===================================================================== 3.
GRUNDPRINZIPIEN
=====================================================================

3.1 LISTENSTANDARD

Jede Administrationsliste besitzt mindestens:

MODEL -> Daten, Filter, Sortierung, Pagination.

VIEW -> stellt Listeninformationen für das Template bereit.

FILTER-XML -> definiert Filter- und Sortierfelder.

TEMPLATE -> stellt die Liste dar.

Alle vier Bestandteile sind verpflichtend.

Für technische Bulk-Aktionen wird zusätzlich der passende Joomla-
Controller verwendet, soweit die Liste solche Aktionen besitzt.

3.2 JOOMLA-6.1-STANDARD

Alle FDShop-Administrationslisten orientieren sich ausschließlich am
nativen Joomla-6.1-Core-Pattern.

Aktuelle Referenz- und Abnahmebasis ist gemäß Architekturquelle Joomla
6.1.x, derzeit Joomla 6.1.3.

Joomla 5.4.x ist kein Entwicklungs- oder Kompatibilitätsziel mehr.

Listen dürfen nicht von Behaviour – Backward Compatibility 6 abhängen.

3.3 SINGLE SOURCE OF TRUTH

Jede Liste besitzt ihre eigene technische Verantwortung.

Filterdefinition -> eigene Filter-XML. Filterzustände -> eigenes
ListModel. View -> stellt Modeldaten bereit. Fachliche Statussemantik ->
zuständige Fachquelle.

3.4 JOOMLA-STANDARD VOR EIGENLÖSUNG

Bevorzugt werden: • ListModel • AdminController für technische
Bulk-Aktionen • Joomla Form API • SearchTools • Pagination • HTMLHelper
• ToolbarHelper • Joomla-Checkboxmechanismen • ACL • CSRF •
Joomla-Standardredirects

Eigene parallele Listenframeworks oder Ersatzmechanismen sind
unzulässig, wenn Joomla den technischen Zweck vollständig erfüllt.

===================================================================== 4.
PFLICHTARCHITEKTUR
=====================================================================

4.1 MODEL

Das ListModel ist verantwortlich für: • filter_fields • populateState()
• getListQuery() • Filter • Sortierung • Pagination •
Datenbereitstellung

Keine Darstellung und keine Businesslogik.

4.2 VIEW

Die View stellt mindestens bereit: this− > itemsthis->state
this− > paginationthis->filterForm $this->activeFilters

Zusätzlich werden die erforderlichen ControlFields vorbereitet.

4.3 TEMPLATE

Verantwortlich für: • Tabellenlayout • SearchTools • Sortierlinks •
Pagination • Checkbox-/Listenbedienung • renderControlFields()

Keine Businesslogik, DB-Zugriffe, Filterlogik oder fachliche
Statusentscheidungen.

4.4 FILTER-XML

Jede Liste besitzt eine eigene Filterdefinition mit mindestens:

Darüber werden Suche, Filter, Sortierung und Limit definiert.

Die Filter-XML definiert nur Filter, die zum tatsächlichen Daten- und
Statusmodell der Liste passen.

4.5 CONTROLLER FÜR LISTENAKTIONEN

Für technische Bulk-Aktionen wird bevorzugt AdminController bzw. der
passende native Joomla-Controllermechanismus verwendet.

Der Controller orchestriert: • Request • Auswahl • ACL • CSRF •
Model-/Service-Aufruf • Meldung • Redirect

Fachliche Lösch-, Schutz-, Status- oder Abhängigkeitsentscheidungen
dürfen dadurch nicht aus dem Service Layer in den Controller wandern.

===================================================================== 5.
MODEL-STANDARD
=====================================================================

5.1 FILTER_FIELDS

Jedes ListModel definiert sämtliche unterstützten Sortierfelder über
filter_fields.

Nur dort freigegebene Felder dürfen dynamisch sortiert werden.

ORDER-BY-Felder aus Request-/Listenzuständen dürfen nicht ungeprüft in
SQL übernommen werden.

filter_fields ist die verbindliche Sortier-Whitelist.

5.2 POPULATESTATE()

populateState() verwaltet: • filter.search • den fachlich tatsächlich
vorhandenen Statusfilter • weitere bereichsspezifische Filter •
list.ordering • list.direction • list.limit

Der Statusfilter wird nicht pauschal als filter.published
vorgeschrieben.

Verwendet der Bereich published, wird der Filter darauf ausgerichtet.

Verwendet der Bereich das bewusst beschlossene is_active, wird der
Filter entsprechend auf is_active ausgerichtet oder über ein klar
dokumentiertes technisches Alias abgebildet, sofern dies im konkreten
Joomla-Mechanismus sinnvoll ist.

Die Listenquelle ändert niemals eigenständig die fachliche
Statussemantik.

5.3 GETLISTQUERY()

getListQuery() ist ausschließlich für den Aufbau der Listenabfrage
verantwortlich.

Zulässig: • Filter • Sortierung • Joins • Where-Bedingungen

Businesslogik und fachliche Berechnungen sind unzulässig.

5.4 STATUSFILTER UND STATUSSPALTEN

published ist kein universeller Zwang für jede FDShop-Entität.

Bestehende und fachlich beschlossene Statusfelder wie is_active bleiben
gültig.

Joomla-Standarddarstellungen wie PublishedButton können verwendet
werden, wenn sie technisch sauber an das tatsächliche Statusfeld und die
fachliche Aktion angebunden werden können.

Ein Joomla-UI-Standard darf nicht dazu führen, dass eine bestehende
FDShop-Fachregel oder Datenstruktur nur aus Namenskonventionsgründen
umgebaut wird.

===================================================================== 6.
VIEW- UND TEMPLATE-STANDARD
=====================================================================

6.1 PFLICHTEIGENSCHAFTEN

Jede Listen-View stellt mindestens bereit: this− > itemsthis->state
this− > paginationthis->filterForm $this->activeFilters

6.2 SEARCHTOOLS

SearchTools werden über den nativen Joomla-6-Layoutmechanismus
LayoutHelper::render() eingebunden.

SearchTools bilden den verbindlichen FDShop-Standard für Filter und
Sortierung in Administrationslisten.

Eigene parallele Filterleisten werden nicht eingeführt, wenn SearchTools
den benötigten technischen Umfang vollständig abbilden.

6.3 CONTROLFIELDS

Notwendige technische ControlFields, insbesondere task, boxchecked und
Token soweit vom verwendeten Joomla-Formmechanismus vorgesehen, werden
über die Joomla-ControlField-/Formmechanik bereitgestellt.

Die Ausgabe erfolgt über renderControlFields().

Manuelle technische Hidden-Fields dürfen diese Mechanik nicht ersetzen.

Fachlich notwendige Hidden-Werte sind hiervon nicht pauschal verboten,
dürfen aber keine Joomla-Steuerfelder duplizieren.

6.4 PAGINATION

Pagination wird über die native Joomla-ListModel-/Pagination-Kette
bereitgestellt.

Eigene parallele Pagination-Logik ist unzulässig, sofern Joomla den
Zweck vollständig erfüllt.

===================================================================== 7.
VERBINDLICHE LISTENREGELN
=====================================================================

REGEL 1 – NATIVE JOOMLA-6-SORTIERUNG

searchtools.sortlist ist projektweit unzulässig.

Sortierlinks werden über den aktuellen Joomla-6-Mechanismus,
insbesondere HTMLHelper::_(‘searchtools.sort’, …), erzeugt, soweit
dieser Mechanismus für die konkrete Liste vorgesehen ist.

REGEL 2 – SEARCHTOOLS VOLLSTÄNDIG

Mindestens erforderlich: • filterForm • activeFilters • vollständige
Filter-XML • renderControlFields()

REGEL 3 – LIST-DEFINITION

Jede Filter-XML enthält . Ohne diesen Bereich sind Sortierung, Limit und
Pagination nicht als vollständiger FDShop-Listenstandard umgesetzt.

REGEL 4 – EIGENE CONTROLFIELDS

Jede Liste verwendet ausschließlich ihre eigenen ControlFields. task,
token, boxchecked und weitere technische Steuerfelder werden nicht
zwischen Listen geteilt.

REGEL 5 – KEINE MANUELLEN TECHNISCHEN HIDDEN-FIELDS ALS ERSATZ

Eigene Hidden-Fields dürfen Joomla-ControlFields nicht ersetzen oder
widersprüchliche technische Zustände erzeugen.

REGEL 6 – EIGENSTÄNDIGER FORM-KONTEXT

Jede Liste besitzt: • eigene filterForm • eigene activeFilters • eigenes
populateState() • eigene Request-Parameter • eigenen Filterzustand •
eigene Pagination

Listen dürfen sich gegenseitig nicht beeinflussen.

REGEL 7 – SEARCHTOOLS NUR FÜR LISTEN

Edit-Formulare rendern keine SearchTools, Listenfilter, Pagination oder
List-ControlFields.

REGEL 8 – LISTEN BEEINFLUSSEN KEINE EDIT-SPEICHERVORGÄNGE

Hidden-Fields, Tasks, ControlFields oder Filterzustände einer Liste
dürfen keinen fremden Edit-Speichervorgang beeinflussen.

REGEL 9 – MEHRERE LISTEN IN EINER ANSICHT

Jede Liste besitzt eigenes
, SearchTools, ControlFields, Filterzustände und Pagination.

REGEL 10 – RENDERCONTROLFIELDS NUR AUS EIGENEM KONTEXT

Ein adminForm rendert ausschließlich die ControlFields seines eigenen
Listenkontexts.

REGEL 11 – STATUSSEMANTIK FOLGT DER FACHQUELLE

Ob ein Bereich is_active, published, state oder einen anderen fachlichen
Status verwendet, wird nicht durch diese Listenquelle entschieden.

Die Liste bildet den fachlich beschlossenen Status Joomla-konform ab.

Eine Umbenennung is_active <-> published erfolgt nicht allein aufgrund
einer Joomla-Core-Namenskonvention.

REGEL 12 – JOOMLA-STANDARDAKTION UND FACHENTSCHEIDUNG GETRENNT

Joomla-Listenmechanismen dürfen technische Aktionen ausführen.

Die fachliche Bedeutung bleibt bei den zuständigen FDShop-Services,
insbesondere bei Löschen, Papierkorb, Wiederherstellen, endgültigem
Löschen und statusbezogenen Abhängigkeiten.

REGEL 13 – ACL UND CSRF

Schreibende Listenaktionen verwenden die vorgesehenen Joomla-ACL- und
CSRF-Mechanismen.

Berechtigungs- oder Tokenprüfungen werden nicht durch Client-Side-Logik
ersetzt.

REGEL 14 – KEINE JOOMLA-5-/BC-LISTENALTLASTEN

Neue Listen dürfen nicht von APIs/Klassen abhängen, die unter Joomla 6
nur durch Behaviour – Backward Compatibility 6 verfügbar sind.

Bestehende Listen werden im Joomla-6-Audit auf solche Altlasten geprüft.

===================================================================== 8.
QUALITÄTSSICHERUNG
=====================================================================

Vor Freigabe einer neuen oder wesentlich geänderten Liste ist mindestens
zu prüfen:

□ native Joomla-6.1-Mechanismen? □ keine BC6-Abhängigkeit? □ eigene
Filter-XML? □ und ? □ eigene filterForm und activeFilters? □
renderControlFields() im eigenen Kontext? □ eigenes populateState()? □
filter_fields vollständig als Sortier-Whitelist? □ keine ungeprüften
ORDER-BY-Felder? □ SearchTools vollständig? □ Pagination funktionsfähig?
□ unabhängig von anderen Listen? □ Statusfilter entspricht tatsächlicher
Fachsemantik? □ kein published/is_active-Umbau nur aus Namenskonvention?
□ schreibende Aktionen mit ACL und CSRF? □ fachliche Entscheidungen im
Service Layer? □ Bulk-Aktionen über vollständige Joomla-Kette?

Administrationslisten müssen mit Architektur, Fachregeln, Governance und
Dokumentationsstandard vereinbar sein.

Beschlossene Zielregel und Ist-Code dürfen gemäß Governance voneinander
abweichen, solange dies korrekt dokumentiert ist.

10. ÄNDERUNGSPROTOKOLL
=====================================================================

V1 Erste Definition des FDShop-Listenstandards.

V2 Joomla-5-SearchTools, Filterstruktur und renderControlFields().

V3 Refactoring, Trennung Listen/Edit, eigenständige Form-Kontexte,
SearchTools nur für Listen, Mehrlisten-Regeln.

V4 Umstellung auf native Joomla-6.1-Entwicklung.

Wesentliche Änderungen: • Joomla-5-Kompatibilitätsziel entfernt • Joomla
6.1.x als verbindliche Listenplattform • BC6-Abhängigkeit ausgeschlossen
• Joomla-6-Core-Pattern präzisiert • AdminController für technische
Bulk-Aktionen ergänzt • Controller-Orchestrierung von
Serviceentscheidung abgegrenzt • filter_fields als Sortier-Whitelist
präzisiert • ungeprüfte ORDER-BY-Felder ausgeschlossen • pauschales
filter.published aus Pflichtzustand entfernt • Statusfilter an
tatsächliche FDShop-Fachsemantik gebunden • is_active und published als
fachabhängige Statusfelder abgegrenzt • keine globale Umbenennung auf
published • PublishedButton nur bei passender Anbindung zulässig •
ACL-/CSRF-Regeln ergänzt • Qualitätscheck auf
Joomla-6.1-/Statuskonsistenz erweitert • früherer Vorschlag einer
gemeinsamen FDShop-Listenbasis nicht als Projektentscheidung übernommen

11. EINWÄNDE / OFFENE PRÜFPUNKTE
=====================================================================

OFFENER PRÜFPUNKT 1

Thema: Joomla-6.1-Audit bestehender Administrationslisten.

Stand: V4 definiert den Zielstandard. Bereits vorhandene Listen wurden
ursprünglich unter Joomla 5.4 getestet und werden im allgemeinen
Joomla-6.1-Repository-Audit gegen V4 geprüft.

Das bedeutet nicht, dass vorhandene Listen pauschal als fehlerhaft oder
inkompatibel gelten.

EINWAND 1

Thema: Keine pauschale Umstellung bestehender FDShop-Statusfelder auf
published.

Begründung: Joomla-Core-Konventionen rechtfertigen allein keine Änderung
einer bewusst beschlossenen FDShop-Fachsemantik.

Die technische Liste folgt dem tatsächlichen fachlichen Statusfeld. Eine
Statusumbenennung benötigt einen eigenständigen fachlichen oder
technischen Grund.
