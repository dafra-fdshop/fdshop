===================================================================== 1.
ZWECK UND ZIELPLATTFORM
=====================================================================

Diese Quelle definiert die verbindliche technische Architektur,
Installationsstruktur und Trennung von Produkt- und Testinfrastruktur.

FDShop wird ausschließlich für Joomla 6 weiterentwickelt. Verbindliche
Zielserie: Joomla 6.1.x Aktuelle Referenz- und Abnahmeversion: Joomla
6.1.3

Joomla 5.4.x ist kein Entwicklungs-/Kompatibilitätsziel mehr und darf
nur als Altsystem bzw. Daten-/Migrationsquelle dienen.

===================================================================== 2.
GRUNDARCHITEKTUR
=====================================================================

Joomla-Standard vor Eigenlösung.

Bevorzugt: • FormController / AdminController • AdminModel / ListModel •
Joomla Table / Form API • MVCFactory / Dependency Injection •
ToolbarHelper / SearchTools • Routing / ACL / CSRF • WebAssetManager

Verantwortungen: Controller -> Request, Orchestrierung, ACL, CSRF,
Redirect Model -> Daten-, Formular- und Listenbereitstellung View ->
Anzeigevorbereitung, keine direkten DB-Abfragen Template -> Darstellung,
keine Business-/DB-Logik Service -> Geschäftsregeln, Validierung,
Mehrtabellenabläufe, Transaktionen Table -> genau eine Tabelle,
technische Persistenz

Single Sources: Komponenten-Boot / Services -> services/provider.php +
Extension-Klasse Manifest -> fdshop.xml Assets ->
media/joomla.asset.json Businesslogik -> Service Layer Workflow ->
FDShop_Projektworkflow

===================================================================== 3.
MVCFACTORY / DI / KLASSENAUFLÖSUNG
=====================================================================

Die Joomla-Standard-MVCFactory ist verbindlich.

Domainservice-Registrierung im DI-Container bedeutet kein beliebiges
Constructor- Autowiring in Joomla-erzeugte Models.

Eine Custom-MVCFactory wird nicht allein für Domainservice-Injection
eingeführt.

Kontrollierter Servicebezug über die gebootete Komponente ist zulässig:
$this->bootComponent(‘com_fdshop’)

Aktuell bewusst so arbeitende Models: • BundleModel • CategoryModel •
CouponModel • ManufacturerModel • ProductModel

Configuration-Unterlisten werden über die Standard-MVCFactory erzeugt.

Datei- und Klassennamen müssen Joomla-/PSR-4-konform und unter Linux
case-sensitiv übereinstimmen. Dies gilt insbesondere für Controller,
Models und Tables.

===================================================================== 4.
REQUEST-, USER- UND DATENKONTEXT
=====================================================================

Domainservices sollen HTTP-/Request-/User-Kontext nicht selbst global
beschaffen, wenn der MVC-Layer die benötigten Werte bestimmen kann.

Bevorzugt: Request/User -> Controller/Model -> gefilterte Werte ->
Service -> Businesslogik

ProductModel übergibt Uploaddaten und User-ID explizit an
ProductService.

Magic-Property-Zugriffe wie Factory::getApplication()->input sind kein
Zielmuster.

===================================================================== 5.
VIEWS / DATENBEREITSTELLUNG
=====================================================================

Views führen keine direkten SQL-/DatabaseInterface-Abfragen aus.
Benötigte Daten kommen aus Models bzw. Services. Direkte
Model-Neuinstanziierung in aktiven Views ist ausgeschlossen.

===================================================================== 6.
EDIT-, SAVE- UND LISTENKETTEN
=====================================================================

Edit-Kette: Toolbar -> Formular -> Request -> Controller -> Model ->
Table/Service -> Redirect -> erneutes Laden

Eigene Save-Endpunkte: • CSRF • passende core.create/core.edit-ACL •
serverseitige Joomla-Formvalidierung • sichere Redirects

Configuration-Referenz: • adminForm • shipmentForm • paymentmethodForm •
orderstatusForm

Requestwurzeln: • shipments[…] • paymentmethods[…] • orderstatuses[…]

Jede Unterliste besitzt eigenen State, SearchTools, Sortierung,
Pagination, ControlFields und Formular-/Task-Kontext.

===================================================================== 7.
ACL / SICHERHEIT
=====================================================================

administrator/access.xml ist die Komponenten-ACL-Quelle.

Core-Aktionen: • core.manage • core.create • core.delete • core.edit •
core.edit.state

Schreibende Endpunkte verwenden CSRF-Schutz. Clientvalidierung ersetzt
keine serverseitige Validierung. Plaintext-Ausgaben gespeicherter
Inhalte werden kontextgerecht escaped.

===================================================================== 8.
ASSETS
=====================================================================

WebAssetManager ist verbindlicher Standard.

Zentrale Assetdefinition: media/joomla.asset.json

Bundle-Asset: com_fdshop.admin-bundle URI: com_fdshop/admin-bundle.js
Aktivierung ausschließlich im Bundle-Editbereich.

===================================================================== 9.
INSTALLATIONSARCHITEKTUR
=====================================================================

fdshop.xml ist zentrale Installationsbeschreibung.

Genau ein aktives Installer-Scriptfile: script.php in der Paketwurzel

administrator/script.php: entfernt administrator/config.xml: entfernt

SQL: administrator/sql/install.mysql.utf8.sql administrator/sql/updates/
administrator/sql/uninstall.mysql.utf8.sql

Install-SQL bildet den vollständigen Fresh-Install-Zielstand ab.
Update-SQL migriert bestehende Installationen. Uninstall-SQL entfernt
den vollständigen aktuellen Tabellenbestand.

Aktueller Schema-/Manifeststand: 0.0.19 Aktueller Tabellenbestand: 32
FDShop-Tabellen.

15. DATENINTEGRITÄT / TRANSAKTIONEN
=====================================================================

Mehrtabellen-Businessabläufe gehören in den Service Layer und sind bei
zusammenhängender Persistenz transaktional auszuführen.

Bestätigtes Bundle-Delete-Muster: BundleModel::delete() ->
BundleService::deleteBundles() -> Transaktion -> bundle_discount_rules
löschen -> bundle_items löschen -> bundles löschen -> Commit / bei
Exception Rollback

Historische Bestell-Snapshots wie order_bundles sind davon getrennt und
dürfen nicht als aktuelle Bundle-Unterdaten mitgelöscht werden.

ERGÄNZENDE VERBINDLICHE ARCHITEKTURDETAILS AUS V5
=====================================================================

INSTALLATIONSSTRUKTUR ≠ SERVERSTRUKTUR

Die Installations-ZIP-Struktur ist nicht identisch mit der späteren
Serverstruktur. Typische ZIP-Wurzel:

administrator/ site/ media/ fdshop.xml script.php language/ (sofern
vorhanden)

Bereits installierte Zielpfade werden nicht in der ZIP vorweggenommen.
Joomla erzeugt bzw. befüllt sie gemäß Manifest.

EXTENSION-DI-CONTAINER

services/provider.php ist die zentrale Registrierungsstelle für
Joomla-Infrastruktur und FDShop-Domainservices im Extension-Child-DI-
Container.

Services werden bevorzugt über Interfaces gebunden, soweit dies dem
bestehenden FDShop-Muster entspricht.

Singleton-Eigenlösungen und globale FDShop-Serviceinstanzen sind
unzulässig.

Factory::getContainer() darf nicht als allgemeiner Service-Locator für
FDShop-Domainservices verwendet werden. Technisch notwendige Zugriffe
auf Joomla-Infrastruktur sind davon nicht pauschal betroffen.

FDSHOP-COMPONENT-FASSADE

Die FDShop-Extension-Klasse darf als kontrollierte
komponentenspezifische Fassade für FDShop-Domainservices dienen.

bootComponent(‘com_fdshop’) ist als Joomla-nativer Komponentenbezug
zulässig. Die Fassade darf nicht zu einem unkontrollierten allgemeinen
Service-Locator werden.

BESTÄTIGTE MVCFACTORY-GRENZE

Die Standard-MVCFactory erzeugt Joomla-MVC-Objekte, löst aber nicht
beliebige FDShop-Domainservice-Konstruktorparameter aus dem
Komponentencontainer auf.

Für die bestehenden Models BundleModel, CategoryModel, CouponModel,
ManufacturerModel und ProductModel ist deshalb der kontrollierte
Komponentenbezug zulässig.

Dabei gilt: • keine Custom-MVCFactory allein zur Erzwingung von
Service-DI • Service zentral in services/provider.php registriert •
keine direkte Service-Erzeugung via new …Service() im Model • kein
globaler Factory::getContainer()-Service-Locator • Businesslogik bleibt
im Service Layer

REQUEST-/USER-KONTEXT

Wenn konkrete Werte genügen, wird nicht das vollständige Application-
oder Request-Objekt an Domainservices weitergereicht.

Globale Benutzerauflösung in CouponService und OrderService ist im
geprüften Auditstand bewusst noch vorhanden und war nicht Bestandteil
des auf ProductService begrenzten Auditbefunds. Daraus entsteht keine
allgemeine Freigabe für neue globale Kontextzugriffe.

EDIT-KETTE

Bei Edit-Bereichen ist vollständig zu prüfen:

Toolbar-Task -> Form-Action -> Record-ID -> Request -> Controller ->
Model -> Table/Service -> Redirect -> erneutes Laden

Bestehende IDs müssen erhalten bleiben. Neuanlagen erzeugen genau einen
Datensatz. Nach dem ersten Save muss die neue ID für Apply/weitere Saves
verwendet werden.

EIGENE SAVE-ENDPUNKTE

Eigene Save-Endpunkte müssen: • CSRF prüfen • core.create/core.edit
passend prüfen • serverseitige Joomla-Formvalidierung durchlaufen •
sichere Redirects verwenden • bestehende IDs bei Apply korrekt erhalten

Clientseitige Validierung ersetzt niemals serverseitige Validierung.

VIEWS UND DATENBEREITSTELLUNG

Models dürfen Daten für die Darstellung effizient anreichern, solange
keine Businessentscheidung in das Model verschoben wird.

Bei Listen ist N+1-Datenbankverhalten zu vermeiden, wenn eine gebündelte
Abfrage möglich ist.

MANIFEST

fdshop.xml bleibt zentrale Installationsbeschreibung.

Eine Umbenennung auf com_fdshop.xml ist ohne technischen Grund nicht
erforderlich.

Manifeständerungen erfolgen nicht aus Kosmetik, sondern nur aus
technischem oder beschlossenem Grund.

SQL UND SCHEMA

Neue Datenbankänderungen erhalten reguläre Update-SQLs.

install.mysql.utf8.sql muss allein das vollständige aktuelle
Fresh-Install- Schema erzeugen. Eine Neuinstallation darf nicht davon
abhängen, historische Update-SQLs nacheinander auszuführen.

Update-SQLs migrieren ausschließlich bestehende Installationen. Bereits
freigegebene/veröffentlichte Update-SQLs werden nicht stillschweigend
nachträglich verändert.

Joomla führt den erreichten Schemastand über den Joomla-eigenen
Schematracking-Mechanismus / #__schemas.

Vor Schemafreigabe prüfen: • Install-SQL enthält vollständigen Zielstand
• neue Update-SQL enthält nur notwendige Migration • Updatefolge
lückenlos • alte Update-SQLs unverändert • Manifest/Schemapfad korrekt •
Uninstall-SQL vollständig

SCRIPTFILE

script.php enthält ausschließlich technische Installationsabläufe, keine
Businesslogik.

Es existiert genau ein aktives Installer-Scriptfile in der Paketwurzel.
administrator/script.php darf nicht wieder als parallele Installerkopie
eingeführt werden.

Für Filesystem-Ordneroperationen gilt Joomla. Joomlaist kein
FDShop-Zielmuster.

FRESH INSTALL UND UPDATE

Fresh Install und Update sind getrennte technische Pfade.

Fresh Install: Manifest + Dateien + vollständige Install-SQL +
Joomla-Script-Lifecycle

Update: bestehender Schemastand + Update-SQL + Datei-/Manifestupdate +
Joomla-Script-Lifecycle

Erfolgreiches Update ersetzt keinen Fresh-Install-Test und umgekehrt.

INSTALLER-FEHLERANALYSE

Bei Installationsfehlern mindestens prüfen: • Manifestidentität/XML •
Dateien/Dateipfade • ZIP-Struktur • Namespace/Autoloading •
scriptfile/Lifecycle • native Joomla-API-Verfügbarkeit •
Install-/Uninstall-SQL • Installationsreste • Joomla-Log/Throwable

ENTWICKLUNGS-/KOMPATIBILITÄTSREGELN

Neue Hauptverzeichnisse benötigen eine Architekturentscheidung.
Joomla-Core-Konventionen werden nicht automatisch zu fachlichen
FDShop-Namensregeln erklärt.

FDShop soll innerhalb der Joomla-6-Zielserie robust gegen reguläre
Wartungs-/Minor-Updates sein. Neue Joomla-6.1.x-Versionen erhalten
gezielte Kompatibilitäts-/Smoke-Tests.

BEWUSST VERBLEIBENDE AUDITSTELLEN

Weiterhin dokumentiert: • komponentenbezogener Servicezugriff in
BundleModel • CategoryModel • CouponModel • ManufacturerModel •
ProductModel • Containerzugriffe in BundleController • OrderController •
OrdersController • FdshopComponent • unterstützte
Factory::*-Verwendungen für Joomla-Kontextfunktionen • globale
Benutzerauflösung in CouponService und OrderService

Diese Stellen sind keine offenen bestätigten Audit-A–D-Blocker.
