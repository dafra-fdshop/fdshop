FDShop – Auftrag: Käuferberechtigung / F3 V1
Datum: 27.09.2026

ZIEL
Vorhandene FDShop-Käufergruppenstruktur fachlich vereinfachen und vollständig durchziehen.

Modell:
- „Ohne Schein (Standard)“
- „Mit Schein (F3-Berechtigung)“

Intern stabile Keys, z.B. standard / permit_holder.
Scheininhaber = Standardberechtigung PLUS F3.
Jeder registrierte Kunde ist IMMER mindestens Standardkunde. Fehlendes/defektes Mapping darf normalen Kauf nie verhindern, aber NIEMALS F3-Rechte verleihen.
F3 entsteht ausschließlich durch ausdrückliche manuelle Adminfreigabe.
Kein Dokumentupload in V1.

1. BESTAND ANALYSIEREN
Aktuellen feature-Stand und Projektdoku vollständig analysieren, insbesondere:

#__fdshop_user_buyer_group_map
#__fdshop_product_buyer_group_map
products.buyer_group_id
orders.buyer_group_id
product.xml buyer_group_ids
ProductService/Model/Table
PurchaseHelper/ProductCardHelper
Cart/Checkout
Bundles/Saved Bundles/Cart Bundles
Admin Order add/update item
Coupons buyer-group mappings
user plugin fdshopprofile
Registration/Profile lifecycle
Packliste
Fixtures/Tests/Caches.

Keine parallele zweite Käufergruppenarchitektur bauen. Vorhandene Vorarbeit bereinigen/fertigstellen.

2. JOOMLA USER BLEIBT BENUTZERVERWALTUNG
Keine eigene Kundenverwaltung.
Joomla #__users bleibt Identity/User Management; FDShop speichert nur fachliche Zusatzberechtigung.
Bestehendes Pluginprinzip erweitern oder kleines sauberes FDShop-User-Plugin nach aktueller Architektur.

Joomla Admin → Benutzer bearbeiten:
zusätzlicher Tab/Bereich „FDShop Käuferberechtigung“.

Käuferstatus:
- Ohne Schein (Standard)
- Mit Schein (F3-Berechtigung)

Hinweis:
„Die F3-Berechtigung darf erst nach manueller Prüfung der erforderlichen Unterlagen vergeben werden.“

Nur berechtigte Admins dürfen ändern.
Keine Joomla User Group als F3-Wahrheit; Joomla-Gruppen bleiben ACL.

3. REGISTRIERUNG / BASELINE
Jeder ordentlich registrierte Benutzer ist mindestens Standard.
Mapping bei Registrierung projektkonform initialisieren, wenn sinnvoll.
Defensiv gilt immer:
registrierter User ohne Mapping = Standard.
Niemals automatisch permit_holder.
Gastregeln nicht nebenbei neu definieren.

4. PRODUKTFELD
Produkt Edit → Allgemein:
genau EIN Pflichtfeld „Käufergruppe“.

Optionen:
- – Bitte auswählen –
- Ohne Schein (Standard)
- Mit Schein (F3-Berechtigung)

required=true.
Für NEUE Produkte KEIN Default.
Speichern ohne bewusste Auswahl muss scheitern.
Keine Mehrfachauswahl, keine Kategorieheuristik.

Aktuell redundante buyer_group_ids/product map/products.buyer_group_id-Struktur analysieren und für Purchase Eligibility auf EINE Single Source of Truth reduzieren. Nicht blind Tabellen droppen, falls anderweitig benötigt.

5. BESTEHENDE PRODUKTE
Fachlich bestätigt: alle aktuell vorhandenen Produkte sind Standardprodukte.
Reguläres idempotentes Update-SQL setzt/migriert alle Bestandsprodukte auf „Ohne Schein (Standard)“.
Daniel führt kein manuelles SQL aus.
Fresh Install und Update identisches Endmodell.

6. STAMMDATEN
Stabile Gruppen:
standard = Ohne Schein (Standard)
permit_holder = Mit Schein (F3-Berechtigung)

Keine hartcodierten zufälligen IDs.
Fresh Install seed.
Update idempotent und bestehende sinnvolle Daten sicher behandeln.

7. ZENTRALE ELIGIBILITY-LOGIK
Eine zentrale fachliche Service-/Helper-Wahrheit, sinngemäß:
userHasF3Permission(userId)
userBuyerStatus(userId)
requiredBuyerStatus(productId)
canPurchaseProduct(userId, productId)
canPurchaseBundle(userId, bundleId)
Batchvarianten wo nötig.

Purchase Action, Cart, Checkout, Bundle und Admin Order dürfen keine jeweils eigene Berechtigungsdefinition/SQL bauen.

8. PERFORMANCE
Keine N+1-Abfragen.
Userberechtigung requestlokal cachen.
Produktanforderungen in Listen/Modulen gebündelt laden bzw. vorhandene Daten nutzen.
Keine Query pro Karte/Modulinstanz.
Checkout/Bundle gebündelt validieren.
Gezielte Performance-/Queryprüfung.

9. F3-RIBBON
F3-Pflichtprodukt zeigt ALLEN Besuchern sichtbares Ribbon „F3“.
Bestehende zentrale Ribbon/ProductCard-Architektur nutzen.
Kategorie, Modul und Produktdetail konsistent, soweit Ribbons dort vorgesehen.
Neu/Hot/etc. nicht regressieren.

10. PURCHASE ACTION
Standardprodukt:
bestehende Regeln unverändert; Standard und Scheininhaber dürfen kaufen.

F3 + Scheininhaber:
normaler Warenkorbbutton, sofern Katalog/Bestand/Login etc. erlauben.

F3 + nicht berechtigt:
Produkt vollständig sichtbar inkl. Preis/Bild/Daten/F3-Ribbon, aber KEIN Add-to-Cart.
An Stelle der runden Purchase Action erscheint optisch passend ein runder „!“-Infoauslöser.
Kein Cart-Request.
Zugänglich: button type=button o.ä., Desktop/Mobile/Tastatur, aria-label „Informationen zur F3-Kaufberechtigung“.

11. F3-INFOMODAL
Bestehende FDShop-Modalarchitektur wiederverwenden, keine neue Popup-Library.

Titel:
„F3 – Kauf nur mit entsprechender Berechtigung“

Sinngemäßer Text:
„Dieser Artikel gehört zur Kategorie F3 und kann nur von entsprechend berechtigten Scheininhabern bestellt werden.

Wenn Sie über eine entsprechende Erlaubnis oder Befähigung verfügen, können Sie uns Ihren Nachweis zur Prüfung einreichen. Nach erfolgreicher Prüfung schalten wir die F3-Kaufberechtigung für Ihr Kundenkonto frei.

Bitte kontaktieren Sie uns zur Freischaltung.“

Schließen.
Sprachstrings.
Kein toter Uploadlink. Späterer Nachweis-Upload muss leicht ergänzbar sein.

12. KATALOGMODUS
Globaler Katalogmodus bleibt stärker: kein Add-to-Cart für niemanden.
F3-Ribbon darf sichtbar bleiben.
Infoauslöser im Katalogmodus nur wenn UX sinnvoll; keine widersprüchliche Kaufaufforderung.

13. SERVERSEITIGER CART-SCHUTZ
UI ist keine Sicherheit.
Jeder Add-to-Cart-Pfad prüft Eligibility.
Manipulierter Standarduser→F3 Request wird abgelehnt:
„Sie sind für das Produkt „XYZ“ nicht berechtigt.“
Kein Cart-Eintrag.
Bestehende Mengen/Bestand/Katalogregeln erhalten.

14. CHECKOUT-ENDPRÜFUNG
Unmittelbar vor Ordererzeugung alle Produkte inkl. Bundle-Inhalte gegen AKTUELLE Userberechtigung prüfen.
Bei unberechtigtem F3:
KEINE Order, Reservierung, Coupon Consumption, Mail.
Meldung:
„Sie sind für das Produkt „XYZ“ nicht berechtigt. Bitte entfernen Sie es aus dem Warenkorb oder melden Sie sich bei uns.“
Mehrere sinnvoll behandeln.
Sicher in bestehender Transaktionsarchitektur.

15. BUNDLES
Enthält Bundle mindestens ein F3-Produkt → Bundle benötigt F3.
Strengste enthaltene Anforderung gewinnt.
Kein manuelles Buyer-Group-Feld am Bundle nötig.
Darstellung/Add-to-cart/Checkout/Saved-Bundle-Pfade soweit relevant absichern.
Kein Umgehen über Bundle.
Keine N+1.

16. ADMIN ORDER
Beim Hinzufügen eines Produkts zur Bestellung Berechtigung des BESTELLKUNDEN prüfen, nicht Adminrechte.
F3 + Kunde ohne F3:
„Der Kunde ist für das Produkt „XYZ“ nicht berechtigt.“
Keine Nebenwirkungen/halbe Speicherung.

Mengenänderung bestehender F3-Position:
historische Orderintegrität respektieren. Wurde Position rechtmäßig bestellt und User verliert später F3, alte Position nicht still entfernen. Eine NEUE Erhöhung/Hinzufügung soll aktuelle Berechtigung verlangen.
Aktuellen Order-Change-Lifecycle sauber analysieren/testen.

17. ORDER-SNAPSHOT – BESTEHENDEN FEHLER BEHEBEN
Aktuell setzt CheckoutService order.buyer_group_id aus cart.items[0].buyer_group_id. Das ist fachlich falsch.

Order.buyer_group_id muss USER-Berechtigung zum Bestellzeitpunkt snapshotten:
Standard → standard
Scheininhaber → permit_holder.
Auch Bundle-only Orders korrekt.

ORDER IS KING:
spätere Useränderung ändert historischen Snapshot nicht.

18. PACKLISTE
Bestehenden Platzhalter in Versandinformationen ersetzen durch:
„Berechtigung/Schein: Ja“
oder
„Berechtigung/Schein: Nein“

Quelle ausschließlich historischer Order-Snapshot.
Nicht aktuelle Userberechtigung bei Regeneration.
Legacy/unklar defensiv „Nein“, niemals erfundenes Ja.

19. COUPONS
Vorhandene coupon buyer-group mappings gegen finales Modell prüfen.
Scheininhaber besitzt Standard + F3; ein für Standardkunden fachlich allgemein erlaubter Gutschein darf nicht versehentlich nur wegen Zusatzberechtigung ausgeschlossen werden, sofern aktuelle allow-Semantik das so meint.
Bestehende allow/exclude-Regeln nicht blind umdeuten.
Nur notwendige kompatible Anpassung; kein Gutschein-Großumbau.
STOP bei fundamentaler Semantikkollision.

20. MANUELLE FREISCHALTUNG
F3 ausschließlich Adminentscheidung.
Späterer Kundenbereich darf Schein/Ausweis hochladen und Admin benachrichtigen, aber Upload darf NIEMALS automatisch freischalten.
Diese Zukunftsregel knapp dokumentieren.
Upload selbst NICHT implementieren.
