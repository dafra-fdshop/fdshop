======================================================================

Der aktuelle PayPal-Sandbox-Flow ist auf der realen IONOS-Testinstallation
erfolgreich abgenommen:

- Payment Session / 10-Minuten-Reservierung
- PayPal Buyer Login
- Buyer Approval
- echter Capture
- FDShop-Bestellung
- Warenkorbabschluss
- Bestellmail-Auslösung
- Abbruchpfad
- PAYMENT.CAPTURE.COMPLETED Webhook
- Webhook-Zustellung PayPal -> FDShop: Success

Webhook-Idempotenz ist damit auch real bestätigt.

Aktuelle Installationsvoraussetzung:

UTC intern, lokale Zeit nur Darstellung.

DIESEN FUNKTIONIERENDEN PAYPAL-FLOW NICHT UMBAUEN.

2. ZIEL
======================================================================

Die Administration einer providergebundenen Zahlungsart soll so gestaltet
werden, dass ein Super User PayPal auch nach Jahren verständlich und sicher
konfigurieren kann, ohne wissen zu müssen, in welcher externen PHP-Datei
Credentials gespeichert werden.

Gleichzeitig bleibt die bestehende Sicherheitsarchitektur erhalten:

- Secrets NICHT in FDShop-DB
- Secrets NICHT im Repository
- Secrets NICHT im HTML/DOM zurückgeben
- externer Secret-Store bleibt tatsächlicher Persistenzort
- Environment bleibt unterstützte und priorisierte Credential-Quelle

Zielbild:

Zahlungsart bearbeiten
-> Allgemeine Zahlungsartfelder
-> Provider = PayPal
-> zusätzlicher Tab "Konfiguration"
-> PayPal-Modus, Credentials, Webhook, Reservierungsdauer, Status und
   Einrichtungshinweise an einem nachvollziehbaren Ort.

Architektur providerfähig vorbereiten.
Aktuell nur PayPal implementieren.
Keine Stripe/Klarna/etc.-Implementierung.

4. TAB "KONFIGURATION" – PAYPAL
======================================================================

Der Tab soll logisch gegliedert sein.

A) STATUS / BETRIEBSMODUS

- Sandbox
- Live

Deutlich sichtbarer Betriebsstatus, z.B.:

PAYPAL SANDBOX AKTIV
oder
PAYPAL LIVE AKTIV

Sandbox und Live besitzen getrennte Credentials.

Live-Umschaltung muss bewusst erfolgen.
Keine versehentliche Aktivierung.

Vor Umschaltung auf Live:
- klare Warnung, dass echte Transaktionen verwendet werden
- Live-Konfiguration auf Vollständigkeit prüfen
- mindestens Live Client-ID
- Live Client Secret
- Live Webhook-ID

Bei unvollständiger Live-Konfiguration:
Aktivierung ablehnen und verständliche Meldung anzeigen.

B) SANDBOX

- Client-ID
- Client Secret
- Webhook-ID
- Webhook URL
- Konfigurationsstatus

C) LIVE

- Client-ID
- Client Secret
- Webhook-ID
- Webhook URL
- Konfigurationsstatus

D) PAYMENT

- PayPal-Reservierungsdauer in Minuten

Die bisherige PayPal-Reservierungsdauer aus global
Konfiguration -> Allgemein soll fachlich in diese Provider-Konfiguration
verschoben werden.

Bestehenden Wert erhalten.
Keine unbeabsichtigte Änderung laufender Konfiguration.

======================================================================
5. CREDENTIAL-DARSTELLUNG
======================================================================

Client-ID:
darf für den Super User angezeigt und geändert werden.

Webhook-ID:
darf für den Super User angezeigt und geändert werden.

Client Secret:
BESTEHENDES SECRET NIEMALS AN DEN BROWSER ZURÜCKGEBEN.

Darstellung sinngemäß:

Client Secret:
"Konfiguriert: Ja"

optional separates leeres Eingabefeld:
"Neues Client Secret"

Regel:
- leer speichern -> vorhandenes Secret bleibt unverändert
- neuer Wert -> vorhandenes Secret wird ersetzt
- niemals bestehendes Secret als value, hidden field, data-Attribut,
  JavaScript-Konfiguration oder HTML-Kommentar rendern

Keine "Secret anzeigen"-Funktion.

Keine Secret-Werte in Logs, Exceptions oder Flash Messages.

======================================================================
6. EXTERNER SECRET-STORE
======================================================================

Bestehender Resolver:

Priorität:
1. nichtleere Environment-Variable
2. externe Secret-Datei
3. nicht konfiguriert

Standard IONOS:
dirname(JPATH_ROOT)/fdshop-data/secrets/fdshop-secrets.php

Alternativ:
FDSHOP_SECRET_FILE

Diese Resolver-Priorität bleibt verbindlich.

Admin-Konfiguration darf die externe Secret-Datei verwalten, sofern sie
beschreibbar ist.

WICHTIG:
Wenn für einen konkreten Wert eine Environment-Variable aktiv ist, darf die
Adminoberfläche NICHT so tun, als könne sie den effektiven Wert durch
Dateischreiben überschreiben.

In diesem Fall:
- Quelle "Environment" anzeigen
- erklären, dass dieser Wert serverseitig verwaltet wird
- Dateieditor für diesen effektiven Wert deaktivieren bzw. Änderung klar
  verhindern

Für dateibasierte Werte:
Quelle "Externe Secret-Datei" anzeigen.

======================================================================
7. SICHERES SCHREIBEN DER SECRET-DATEI
======================================================================

Kein naives file_put_contents direkt auf die produktive Datei.

Anforderungen:

- Pfad ausschließlich aus bestehendem Resolver/konfigurierter
  FDSHOP_SECRET_FILE-Logik
- keine frei eingebbare Dateipfad-Manipulation im Paymentformular
- bestehende Sandbox-/Live-Werte erhalten, sofern nicht geändert
- atomisches Schreiben über temporäre Datei + Rename/Replace soweit
  Hosting/Filesystem dies unterstützt
- restriktive sinnvolle Dateirechte versuchen, ohne Shared-Hosting unnötig
  unbrauchbar zu machen
- PHP-Datei syntaktisch valide erzeugen
- keine Secrets in Fehlermeldungen
- bei Schreibfehler: bestehende Datei unverändert lassen
- keine teilweise/kaputte Credential-Datei
- Race-/Parallel-Save-Risiko soweit sinnvoll berücksichtigen
- Eingaben validieren/trimmen ohne Credentials fachlich zu verstümmeln

Vor Schreiben prüfen:
- existiert Store?
- lesbar?
- beschreibbar?
- Verzeichnis beschreibbar?

Wenn nicht beschreibbar:
keine Konfiguration zerstören.

======================================================================
8. FALL: SECRET-STORE NICHT BESCHREIBBAR
======================================================================

Die Adminseite bleibt trotzdem brauchbar.

Dann deutlich anzeigen:

"Der externe FDShop-Secret-Store kann von Joomla nicht beschrieben werden.
Die PayPal-Zugangsdaten müssen serverseitig gepflegt werden."

Zusätzlich für Super User:
- verwendete Credential-Quelle
- sinnvoller/effektiver Secret-Pfad bzw. sicher dargestellter Pfadhinweis
- erwartete Struktur
- Hinweis auf FDSHOP_SECRET_FILE, wenn verwendet

Keine Secrets anzeigen.

Ziel:
Daniel soll auch in 2–4 Jahren sofort erkennen:
- WO die Werte liegen
- WARUM sie hier ggf. nicht editierbar sind
- WAS serverseitig geändert werden muss

9. WEBHOOK UX
======================================================================

Webhook URL automatisch aus der aktuellen Site/Route korrekt ableiten.

Anzeige:
- Webhook URL
- Kopiermöglichkeit, wenn Joomla-konform/einfach umsetzbar

Einrichtungshinweis:

PayPal Developer Dashboard
-> Apps & Credentials
-> betreffende Sandbox-/Live-App
-> Webhooks
-> Add Webhook
-> angezeigte FDShop Webhook URL
-> Event "Payment capture completed"
-> erzeugte Webhook-ID hier eintragen

Benötigtes Event ausdrücklich anzeigen:

PAYMENT.CAPTURE.COMPLETED

Nicht "All Events" empfehlen.

Webhook URL ist kein Secret.

Webhook-ID ist kein Client Secret, aber weiterhin nur im Admin-Kontext
verwalten.

11. RESERVIERUNGSDAUER
======================================================================

PayPal-Reservierungsdauer aktuell global konfiguriert.

In den PayPal-Konfigurationstab verschieben.

Bestehende Fachgrenzen beibehalten:
mindestens 5, maximal 30 Minuten
Default 10 Minuten

Keine Änderung am Reservierungsmodell selbst.

Wert darf weiterhin in bestehender Config-Persistenz liegen, sofern dies
architektonisch sinnvoll ist; Ziel ist primär fachlich korrekte Admin-UX.

Wenn mehrere PayPal-Zahlungsarten technisch möglich wären, prüfen und
dokumentieren, ob Reservierungsdauer providerweit oder paymentmethodbezogen
sein soll.

Keine unnötige Schemaänderung ohne Analyse.
