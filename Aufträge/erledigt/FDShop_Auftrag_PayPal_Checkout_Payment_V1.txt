1. ZIEL / SCOPE
FDShop erhält eine robuste einmalige PayPal-Zahlung im bestehenden Warenkorb.
Nicht Scope: Advanced Card, Apple Pay, Google Pay, Fastlane, Vaulting,
Subscriptions, Refund-Funktion, weitere Provider.
Leitsatz: PAYMENT bestätigt Geld. ORDER besitzt Bestellung, Lager, Gutschein,
History, Mail und Dokumente. PRODUCT IS KING / ORDER IS KING. Server-side first.

3. BESTEHENDER FLOW
Aktuell erzeugt CartController::checkout()->CheckoutService::createOrder()
unmittelbar die Order. Für normale Zahlarten muss das funktional erhalten
bleiben. Vorhandenes payment_methods.paypal_enabled verwenden:
0 = bestehender Flow; 1 = PayPal-Flow. Keine hardcodierte Payment-ID, kein
zweiter Warenkorb.

4. PAYPAL-FLOW
PayPal zwingend zweistufig:
a) Kauf serverseitig vollständig revalidieren.
b) interne Payment Session/Snapshot erzeugen.
c) Ware temporär reservieren.
d) PayPal Order serverseitig erzeugen.
e) Käufer genehmigt bei PayPal.
f) Capture serverseitig durchführen/verifizieren.
g) nur nach nachweislich erfolgreichem Capture FDShop-Order atomar finalisieren.
h) erst danach Cart löschen.
i) Mail/PDF/Dokumente erst nach Orderfinalisierung.
Vor Capture keine normale FDShop-Order.

5. PROVIDERNEUTRALES DATENMODELL
Keine paypal_* Paymentarchitektur in orders. Mindestens sinngemäß:
#__fdshop_payment_sessions und #__fdshop_payment_transactions.
Session: eindeutige ID/Token, user_id, provider, payment_method_id, sicherer
serverseitiger Kaufsnapshot, amount, currency, interner Status,
provider_order_id, expires_at, created/modified, spätere order_id,
Idempotenz/Finalisierung.
Transaction: session_id, provider, provider_order_id, capture/transaction_id,
Providerstatus, amount/currency, Capture-/Verifikationszeit,
Finalisierungszustand, sinnvolle Fehler-/Retryinfo, created/modified.
UNIQUE Constraints/Locks gegen Doppelverarbeitung.
Neue Update-SQL + vollständiges Install-/Uninstall-SQL + Schema/Manifest hoch.
Alte veröffentlichte Update-SQLs nicht ändern.

6. REVALIDIERUNG / SNAPSHOT
Beim tatsächlichen PayPal-Start serverseitig neu prüfen: User/Eigentümer,
Katalogmodus, AGB, Zahlart/paypal_enabled, Abhol-/Versandart, Cart nicht leer,
Produktstatus/Publikation, F3 Buyer Eligibility, Bundles, physische Nachfrage,
Bestand, Preise/Aktionspreise, Verpackung, Gebühren, Gutschein/Gültigkeit/
Limits, Währung, Gesamtsumme. Clientwerte für Preis/amount/currency/Rabatt/
Lagerbedarf niemals als Wahrheit übernehmen. Snapshot muss spätere sichere
Finalisierung ermöglichen und bestehende FDShop-Snapshotregeln wiederverwenden.

7. TEMPORÄRE RESERVIERUNG
Keine Reservierung durch normalen Warenkorb, Zahlungsartauswahl oder Seitenaufruf.
Erst beim tatsächlichen Start der PayPal-Zahlung: revalidieren, betroffene
Bestände in stabiler Reihenfolge sperren, Verfügbarkeit prüfen, temporär atomar
reservieren, serverseitiges expires_at speichern.
Standard 10 Minuten; Admin-konfigurierbar, zulässig 5–30 Minuten.
Reservierung eindeutig Session zuordnen; keine parallele Bestandswahrheit.
Bei erfolgreicher Finalisierung möglichst atomar in normalen Order-Lagerzustand
überführen, ohne unnötige Freigabelücke durch -qty/+qty.

8. COUNTDOWN / EXPIRY / CLEANUP
Browser zeigt SERVER-expires_at, z.B. 09:47.
Texte sinngemäß: „Zeit für den Abschluss Ihrer Zahlung“ und
„Bitte schließen Sie den Bezahlvorgang innerhalb der verfügbaren Zeit ab.“
Nicht erklären, dass Produkte 10 Minuten reserviert sind.
00:00: Vorgang abgelaufen; erneuter Start = vollständige Revalidierung/neue
Session nur wenn möglich. Browser ist nie Cleanup-Wahrheit.
Zustände sinngemäß created/reserved/payment_in_progress/capturing/completed/
expired/failed. Sobald Capture beginnt atomar -> capturing. Cleaner darf
capturing nie freigeben. Race expiry vs capture mit Locks/atomaren Übergängen.
Expired ohne Capture: Reservierung genau einmal frei; Cart bleibt; kein Coupon,
keine Order/Mail/Dokumente.
Cleanup bevorzugt Joomla Scheduled Task + opportunistisch an sicheren Stellen.

9. PAYPAL API / JS SDK V6
Aktuelle offizielle PayPal-Dokumentation verwenden. Orders REST API v2,
JavaScript SDK v6, intent CAPTURE. Create Order serverseitig, Capture
serverseitig. SDK v6 nicht wie v5 implementieren; aktuelle Callbacks und
Return-Shapes prüfen. Für normalen einmaligen PayPal-v6-Checkout darf die
öffentliche Client-ID gemäß PayPal-Doku im Browser zur SDK-Initialisierung
verwendet werden. Client Secret ausschließlich serverseitig. Keinen
Fastlane-spezifischen Client-Token-Flow einführen, da Fastlane out of scope,
sofern aktuelle Doku für den tatsächlich verwendeten normalen PayPal-Flow
keinen verlangt. Provider-HTTP in eigenem Service; keine PayPal-Businesslogik
in Template/JS. Access Tokens/Secrets nie loggen. Timeouts/kontrollierte Fehler.

10. STATUS / GELD
Capture COMPLETED = Zahlungsnachweis -> amount/currency prüfen -> Transaction
persistieren -> Finalizer.
PENDING = nicht bezahlt, keine bezahlte Order.
DECLINED/FAILED/endgültiger Fehler = keine Order, Cart bleibt, kein Coupon,
keine Mail/Dokumente, Reservierung kontrolliert freigeben wenn sicher.
Vor Finalisierung internen erwarteten Betrag/Währung gegen PayPal Order/Capture
prüfen. Abweichung = keine Finalisierung. Keine Preisangleichung. Geldwerte
ohne Float-Rundungsfehler vergleichen.

11. EIN IDEMPOTENTER FINALIZER
Browser und Webhook dürfen keine getrennten Ordererzeugungswege haben.
Beide -> derselbe Finalizer. Garantieren: exakt eine Order, Coupon-Nutzung,
Lagerübernahme, History, Mail/Dokumenterzeugung. Locks + UNIQUE Constraints.
Bestehende submission_id-/Idempotenzlogik sinnvoll integrieren.

12. CAPTURE OK, LOKALE FINALISIERUNG FEHLER
Nach erfolgreichem Capture NIEMALS erneut capturen. Transaction merkt Capture
dauerhaft. Lokale Finalisierung retryfähig. Späterer Browserrequest oder
verifizierter Webhook erkennt Capture und versucht nur fehlende FDShop-
Finalisierung erneut. Diagnose ohne Secrets/Tokens.

13. ORDERFINALISIERUNG
Erfolgreiche PayPal-Order direkt mit bestehendem aktiven Status „paid“
erzeugen/finalisieren; Status vorher real prüfen, keinen neuen erfinden.
Bestehende Checkout-/Orderlogik sinnvoll refaktorieren und gemeinsame
Ordererzeugung wiederverwenden; createOrder()-Logik NICHT komplett kopieren.
Finalisierung prüft Session/Eigentümer, Capture, amount/currency, Idempotenz,
F3, Gutschein, Lager/Reservierung. Coupon erst atomar bei erfolgreicher Order
verbrauchen. Post-Capture-Fachkonflikt: Capture/Transaction erhalten, kein
Recapture, retryfähig/diagnostizierbar; nötige neue Businessentscheidung = STOP.

14. CART / UX
Cart bleibt bei Popup schließen, Reload, Cancel, PENDING, DECLINED/FAILED,
Expiry und API-Fehler vor Capture. Erst nach erfolgreicher Finalisierung Cart
und passende Sessionwerte bereinigen.
Bestehenden Warenkorb nutzen. paypal_enabled=1: „Zahlungspflichtig bestellen“
startet PayPal statt sofort Order. SDK v6 Joomla-konform/WebAssetManager.
Eligibility, Loading/Fehler, Popup-Blocker/Abbruch sauber. Reload laufender
Session sicher wieder aufnehmen oder kontrolliert auflösen.
