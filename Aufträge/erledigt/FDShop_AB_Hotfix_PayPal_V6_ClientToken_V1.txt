1. NEUER REALBEFUND
======================================================================

Der vorherige Hotfix zur transienten Browseraktivierung ist technisch sinnvoll,
hat den realen IONOS-Fehler aber NICHT behoben.

Nach Installation des Hotfixes hängt das PayPal-Sandbox-Popup weiterhin
reproduzierbar bei:

„Sie werden zu PayPal weitergeleitet“

Gegenproben mit:
- Edge normal
- Edge InPrivate
- Chrome
- Mobilgerät

Alle zeigen dasselbe Verhalten.

Damit ist ein einzelnes Browserprofil/Cookieproblem sehr unwahrscheinlich.

Real bestätigt:
- payment.start HTTP 200
- gültige interne Payment Session
- gültige PayPal Sandbox Order-ID
- Betrag/Währung korrekt
- Reservierung korrekt
- PayPal OAuth/Create Order erfolgreich
- PayPal Popup wird geöffnet
- PayPal-interne Requests überwiegend HTTP 200
- Firebase WebSockets 101 Switching Protocols

Im PayPal-Popup selbst erscheinen wiederholt PayPal-interne Firebase-Warnungen
über ungültige Authentication Credentials. Keine offensichtlichen 4xx/5xx
wurden im Popup-Network beobachtet.

Kein Capture wurde ausgelöst.

2. ZIEL DIESES AUFTRAGS
======================================================================

Kontrollierter A/B-Test:

Bisher:
window.paypal.createInstance({ clientId: ... })

Jetzt testweise:
browser-safe clientToken serverseitig gemäß aktueller offizieller PayPal-v6-
Dokumentation erzeugen und createInstance damit initialisieren.

Nur diese Authentifizierungsvariante ändern.

Wenn clientToken den realen Buyer-Flow behebt, kann diese Variante beibehalten
werden.

Wenn der Flow damit ebenfalls hängt:
- NICHT weitere Checkoutbereiche spekulativ umbauen
- Befund sauber berichten
- nächster Schritt wird eine isolierte PayPal-Minimalintegration/App-
  Konfigurationsprüfung außerhalb der FDShop-Fachlogik.

======================================================================
3. DOKUMENTATIONSLAGE
======================================================================

Die aktuelle offizielle PayPal-v6-Dokumentation ist widersprüchlich:

- Quickstart / Teile der v5→v6-Doku zeigen clientId für Standard-One-Time-
  Payments.
- Andere aktuelle Setup-/Upgrade-Seiten zeigen bzw. verlangen browser-safe
  clientToken für createInstance.

Daher ist dieser Auftrag ausdrücklich ein A/B-Realtest und keine Behauptung,
dass clientId grundsätzlich ungültig ist.

Bitte vor Implementierung aktuelle offizielle PayPal-Dokumentation noch einmal
prüfen und den tatsächlich verwendeten Endpoint/Parameter daraus ableiten.

======================================================================
4. CLIENT-TOKEN-IMPLEMENTIERUNG
======================================================================

Falls gemäß aktueller PayPal-Doku technisch möglich:

- Token ausschließlich serverseitig mit Client-ID + Client-Secret erzeugen.
- Sandbox/Live korrekt trennen.
- Offiziellen PayPal-Endpunkt und erforderliche Parameter verwenden.
- Domainbindung/Domainparameter korrekt auf den aufrufenden Shop beziehen,
  soweit von PayPal für den Token vorgesehen.
- Secret niemals an Browser.
- normaler serverseitiger OAuth Access Token niemals versehentlich als
  ungeeigneter Browserwert exponieren.
- ausschließlich den browser-safe Wert zurückgeben, den PayPal für
  createInstance(clientToken) vorsieht.
- Ablaufzeit respektieren.
- kein DB-Persistieren nötig, sofern nicht zwingend.
- keine Tokens/Secrets loggen.
- Fehler sauber und ohne Credential-Leak behandeln.
- vorhandenen zentralen Credential Resolver verwenden.

Frontend:
- Client Token vor Freigabe der PayPal-Bestellaktion beschaffen.
- SDK/Eligibility/Payment Session weiterhin vollständig vorbereiten, bevor
  Button aktiv wird.
- session.start() weiterhin unmittelbar im echten Benutzerklick.
- createOrder-Promise NICHT vor start() awaiten.
- presentationMode auto beibehalten.
- serverseitiges payment.start/Create Order unverändert lassen.
