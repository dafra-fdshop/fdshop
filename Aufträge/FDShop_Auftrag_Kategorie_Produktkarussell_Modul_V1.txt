FDShop – Auftrag: Kategorie-Produktkarussell-Modul V1
Datum: 25.09.2026

ZIEL
Ein neues wiederverwendbares FDShop-Frontendmodul erstellen, das Produkte einer gewählten FDShop-Kategorie performant als horizontale Produktkarten/Carousel ausgibt.

Auf der Startseite werden realistisch 6–8 oder mehr Instanzen gleichzeitig eingesetzt, jeweils mit anderer Kategorie, z.B. Frisch eingetroffen, Aktionen, Batterien, Verbünde oder Raketen.

Das Modul übernimmt die bewährte Idee des bisherigen VirtueMart-Produktmoduls, wird aber Joomla-6-konform, server-side first und deutlich performanter umgesetzt.

MODULTYP / PAKET
Neues eigenständiges Joomla-Site-Modul im bestehenden FDShop-Paket. Sinnvollen technischen Namen selbst wählen, z.B. mod_fdshop_products.

Nicht das Filtermodul zweckentfremden.

pkg_fdshop muss das Modul automatisch mitinstallieren/aktualisieren. Keine separate manuelle Installation im normalen FDShop-Paketworkflow.

FRONTEND
Eine Instanz zeigt:
- Modulüberschrift
- optional "Zur Kategorie"
- Produkte der konfigurierten Kategorie
- horizontale Carousel-Navigation, wenn mehr Produkte vorhanden sind als gleichzeitig sichtbar

Produktkarte nur mit:
- Produktbild
- vorhandenen relevanten Ribbons/Badges
- Produktname
- technischen Kurzdetails/Icons entsprechend Kategorieansicht
- Preis
- ggf. altem/regulärem Preis bei Angebot
- Warenkorb-Button

Keine langen Beschreibungen.

PRODUKTKARTEN / WIEDERVERWENDUNG
Optisch möglichst dieselbe FDShop-Produktkartensprache wie Kategorieansicht verwenden: Hintergrund, Abstände, Ribbons, Preislogik, technische Icons, Media, Warenkorbbutton.

Gemeinsame Partials/Layoutbausteine oder kleine saubere Extraktion bevorzugen, wenn ohne riskante Großrefaktorierung möglich.

Keine dauerhaft auseinanderlaufende Kopie derselben Fachlogik. Aber auch keine große Kategorie-Frontend-Neuarchitektur nur für dieses Modul.

KATEGORIE
Administrator wählt eine aktive FDShop-Kategorie über Joomla-konforme Auswahl. Keine manuelle Kategorie-ID als Standard-UX.

Nur fachlich sichtbare/aktive, nicht gelöschte Produkte gemäß bestehender FDShop-Katalogregeln.

"Zur Kategorie":
- optional
- Ziel automatisch aus gewählter Kategorie
- Buttontext konfigurierbar, Default "Zur Kategorie"
- FDShop/Joomla Router, SEF-kompatibel

PRODUKTANZAHL / RESPONSIVE
Maximale Produktzahl konfigurierbar, sinnvoller Default z.B. 20. Typischer Zielbereich 5–25.

Desktop-Default: 5 sichtbare Karten.
Responsive ungefähr:
- großer Desktop 5
- Tablet 3
- Mobil 1–2

Exakte Breakpoints an bestehender FDShop-/Bootstrap-Struktur ausrichten. Keine leeren Karten.

CAROUSEL
Bevorzugt Bootstrap 5 über Joomla WebAssetManager.

Kein externes Slider-Paket und keine große eigene JS-Bibliothek.

Mehrere Modulinstanzen müssen konfliktfrei funktionieren:
- eindeutige Carousel-IDs
- Navigation nur für eigene Instanz
- keine globale JS-Kollision

Links/rechts nur wenn mehrere Slides vorhanden. Sinnvolle aria-labels. Keine Auto-Rotation als Default.

KEIN AJAX-NACHLADEN V1
Alle konfigurierten Produktdaten serverseitig effizient laden. Carousel-Pfeil löst keinen Serverrequest aus.

20–25 Produktdatensätze sind klein; Bilder sind der größere Transferfaktor. Geeignete Bilder lazy laden.

Keine neue AJAX-API nur fürs Modul.

PERFORMANCE – KERNANFORDERUNG
6–8+ Instanzen gleichzeitig sind Normalfall.

Explizit gegen N+1 und redundante DB-Arbeit bauen.

Benötigte Karteninformationen möglichst über gebündelte Queries/Batch-Lookups laden:
- Kategoriebezug
- Preis/Aktion
- Media
- technische Kurzdetails
- Ribbons
- Bestandsanzeige

Nicht pro Produkt mehrere Einzelqueries. Keine vollständigen Produktdetailobjekte laden, wenn nur Kartendaten benötigt werden.

Performance-Abnahme:
- mindestens 1 Modul und 8 Module vergleichen
- repräsentativ bis ca. 20 Produkte/Instanz bzw. geeignete Fixtures
- Queryverhalten beobachten
- Renderzeit grob messen
- keine offensichtliche N+1-Explosion

Tatsächliche Beobachtungen/Messwerte im Abschlussbericht nennen.

CACHE
Joomla-Modulcache/Cachemechanismen verwenden, kein eigenes Cacheframework.

Konfiguration:
- Cache gemäß Joomla/global bzw. verwenden
- Cache deaktivieren
- Cachezeit

Sinnvoller Default z.B. 300/600 Sekunden nach Projektkonvention.

Kaufkritische Entscheidungen niemals allein aus gecachtem HTML. Add-to-cart/Checkout validieren Produkt, Preis, Menge und Bestand weiterhin serverseitig aktuell.

Bestehende Cache-Invalidierung sinnvoll nutzen, falls vorhanden. Keine große neue Invalidierungsarchitektur nur für V1.
